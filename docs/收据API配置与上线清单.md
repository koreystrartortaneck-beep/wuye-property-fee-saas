# 收据 API 配置与上线清单

## 现在完成了什么

管理端只读收据接口已在开发分支实现：

`GET /api/v1/admin/payments/:orderNo/receipt`

配套搜索接口：`GET /api/v1/admin/payments/receipt-search?keyword=关键词`。支持当前房屋联系人手机号/姓名、房号/显示名称、收据编号、订单号，包含合并支付的各房屋。手机号按当前 HouseContact 查询，不用已冻结的旧 ownerPhone，也不向前端批量返回联系人号码。页面输入后 300ms 发起搜索，结果继续按当前渠道和状态筛选；此搜索接口也要随收据接口发布，旧服务会明确报不支持。

使用现有管理端身份认证和租户限定，返回订单对应的原电子收据；退款订单标记作废。它不是新的微信支付下单接口，也不是微信官方出具的电子发票。这里展示的是系统依据实际支付订单生成的物业电子收据，沿用业主缴费后原有格式。

列表默认只显示 `channel=WXPAY` 且 `status=SUCCESS` 的收据；OFFLINE 单独分类，MOCK 不展示。已退款在微信分类的筛选里单独查看，不计入实收。人工登记的现金、转账，即使来自微信转账，也不算本系统的小程序微信支付。

代码已开发不等于线上已可用：现有生产环境此前检查仍缺少新详情路由。更改列表分类或前端文案不能补齐后端。

## 用户需要准备什么

不用新申请商户号、不用添加新的支付回调、不用重新提供 APIv3 密钥。这个接口读取现有订单与收据快照，不调用新的微信商户 API。

需要具备当前微信云托管项目的管理/发布权限。在你操作的电脑登录微信云托管控制台，打开现有服务 `wuye-api`，把以下不含密钥的配置页面截图给协助部署的 AI：

- 当前服务名称、所属环境及正在运行的版本/提交。
- 代码仓库、自动构建分支和触发方式。
- 构建目录、Dockerfile 路径、容器端口。
- 当前健康检查路径、流量分配和可回滚版本。

不要发送密码、数据库连接串、JWT_SECRET、支付密钥、私钥、Cookie 或令牌。需人工填写的秘密仍留在云控制台；不是把账号密码交给 AI。

## 本仓库可核对的配置

这些是源码期望，不代表已重新核验云控制台当前配置：

- 构建上下文：仓库根目录。
- Dockerfile：根目录 `Dockerfile`。
- 容器端口：`3000`（现有 PORT 如不同，先对照当前服务，不直接改）。
- 运行启动：现有 Dockerfile 自动执行 `prisma migrate deploy` 后启动 API。
- 原有数据库、JWT、微信及支付环境变量全部保留。本收据接口不增加环境变量，也没有新增数据库迁移。
- 保留现有网络/VPC、数据库连接、健康检查、回调域名和入口，不为收据功能新建空数据库。
- 原小程序 `config.js` 的 `useCloud`、`cloudEnv`、`cloudService` 在更新同一服务时无需改变。

## 怎么安排发布

目前 `feat/property-staff-workspace` 除收据外，还含欠费分页、报修详情、草稿部分发布。**不要为了开通收据，直接把整个分支合并 main 或让生产跟踪此开发分支。** 仓库文档注明 main 会触发生产构建。

用户确认部署范围后，建议协助 AI 先整理“只含收据所需 API 改动”的发布候选：管理收据路由、共用收据读取与权限测试，以及列表房屋过滤等所需依赖；不要机械复制整个文件夹，避免夹带账单发布变更。先在隔离环境联调，再明确授权上线。

上线前核对当前分支、数据库迁移差异、备份状态及旧版本回滚方式；将实际配置和缺项列出来确认。未获授权不点击部署，不推 main。

## 上线后怎样证明真的好了

1. 核对构建版本对应批准的提交，不能只看“运行中”或健康检查成功。
2. 用物业管理账号，对已存在的真实微信成功订单调用新 GET 接口，确认 `code=0`，订单号、实收金额、收据编号和快照一致；不通过制造真实收款来测试。
3. 确认无登录被拒绝、跨租户不可读；租户隔离用隔离环境测试账号验证，不猜测其他租户真实订单号。
4. 已退款订单显示作废，金额不进入有效实收；线下登记不进入微信分类；测试支付不进入任一正式分类。
5. 手机预览“微信支付 → 收据详情 → 保存收据”，再与业主同一订单的收据核对。相册权限、长内容和真机视觉均需实测。

若仍返回 404：先核对实际云环境/服务及部署提交，不要放开权限，不要用收款列表拼造收据。若服务异常，按已确认的旧镜像版本回滚；不要回滚或删除财务数据。
