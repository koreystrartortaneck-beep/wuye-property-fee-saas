# 部署顺序与验证

写这份文档是因为 2026-08-01 我把顺序搞反了,让物业在后台看到了一句假消息。

## 顺序:先 API,后后台静态资源

后台是纯静态资源(rsync 到 nginx),**上线是秒级的**;API 走 GitHub → 微信云托管自动构建,
**要 6–10 分钟**。所以如果先传后台:

> 那段时间里,后台的新按钮会去调一个还不存在的接口。

2026-08-01 的实际后果:我先部署了带「退款溯源」的后台,API 还没上,
于是点那个按钮时前端捕获了 404、把 `refundDetail` 置为 null,
界面显示 **「该订单暂无退款记录」**——而记录明明是有的。
**假消息比报错更糟**:报错会让人来问,假消息会让人相信。

正确顺序:

```bash
# 1) 先推 API，等它真的上线（见下面「怎么确认上线」）
git push origin main

# 2) 确认新接口能通之后，再传后台
cd apps/admin && pnpm build:prod
rsync -rlptz --delete dist/ motuo:/opt/wuye/admin/
ssh motuo 'chmod -R u=rwX,go=rX /opt/wuye/admin'
```

如果前端改动**不依赖新接口**(纯样式、纯文案),顺序无所谓。
判据很简单:这次前端改动有没有调用新增的路径。

## 怎么确认 API 真的上线了

**不要看 uptime。** 重启只说明「有一次部署发生过」,不说明是哪个提交 ——
连续推两次时,你看到的重启很可能是上一个提交的。

可靠做法:**探一个这次新增的端点**。

```bash
API=https://wuye-api-285165-10-1456585997.sh.run.tcloudbase.com/api/v1
TOK=$(curl -s --noproxy '*' -X POST "$API/admin/auth/login" -H 'Content-Type: application/json' \
  -d "{\"username\":\"$ADMIN_USER\",\"password\":\"$ADMIN_PASS\"}" \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

# code=0 表示已上线；code=40400 表示还没
curl -s --noproxy '*' "$API/<这次新增的路径>" -H "Authorization: Bearer $TOK" \
  | python3 -c "import sys,json;print(json.load(sys.stdin).get('code'))"
```

注意 `/health` 与 `readiness` 都**不能**用来判断版本:它们在新旧版本里都存在。
`readiness` 里的 `schemaVersion.latestInImage` 只在有新迁移时才变。

如果这次改动没有新端点(比如只改了内部逻辑),那就只能靠行为验证 ——
所以**每次有可观测差异的改动,顺手加一个能探的标记是值得的**。

## 构建看起来卡住了怎么办

正常 6–10 分钟。超过 15 分钟基本可以判定异常。

先排除代码问题(这三步本地都能做完):

```bash
cd apps/api && npx tsc --noEmit -p tsconfig.json   # 类型
cd apps/api && pnpm build                          # 就是容器里跑的 nest build
git log --since="today" --name-only --pretty=format:'%h' | grep -E "package.json|pnpm-lock"
```

最后那条是因为 Dockerfile 用了 `pnpm install --frozen-lockfile`:
**package.json 改了而 lockfile 没跟着改,构建会直接失败**,而本地 `pnpm build` 完全看不出来。

三步都干净就是平台侧的事。我们这边没有构建日志的可见性(云托管不回执),
能做的只有两件:

1. 去微信云托管控制台看构建记录 —— 这是唯一能看到失败原因的地方
2. 推一个新提交重新触发

2026-08-01 实测:一次推送 56 分钟没有部署,而 `tsc`、`nest build`、lockfile 三项全干净。

## 容器里到底跑什么

根目录 `Dockerfile`(云托管要求名称不含路径,内容与 `deploy/Dockerfile.api` 一致):

- 只构建 `@pf/shared` 和 `@pf/api`,**不跑 lint、不跑测试**
  → 所以测试红了照样能部署上去。跑测试是推送前的事,别指望构建拦你。
- 启动命令 `npx prisma migrate deploy && node dist/apps/api/src/main.js`
  → 迁移在启动前自动应用。迁移失败服务起不来,而**失败原因只在容器日志里**,
    这也是 readiness 里要有 `SCHEMA_MIGRATIONS` 那一项的原因。
