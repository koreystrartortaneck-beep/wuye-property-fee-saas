## 基线与范围

- 基于远端 main `a37e5fca65a94ad2341f32108281a58020b00567`，与用户提供的 wuye-api-211 版本备注相符。开始准备时已重新 fetch 核对。
- 独立候选分支：`release/receipt-api-only`。不是将 `feat/property-staff-workspace` 整体合入。
- 仅两份运行时源码变更：`admin-payment.controller.ts`、`payment.service.ts`；其余是收据和搜索测试及本文。
- 新增只读 `GET /api/v1/admin/payments/:orderNo/receipt`、`GET /api/v1/admin/payments/receipt-search?keyword=...`。
- 收款列表补充房屋过滤、稳定分页、订单 ID/合并付款账单 ID；旧调用不传新参数时保留原查询范围。
- 搜索覆盖房号/显示名称、当前 HouseContact 手机号/姓名、收据号/订单号及合并支付房屋；联系人号码不随列表返回。
- 管理收据使用当前管理员租户条件；业主仍校验订单所属用户；共用既有快照与历史回退生成逻辑，退款标记作废。

## 明确排除

没有草稿部分发布、欠费分页、报修接口、小程序 UI、支付回调、退款操作、计费规则、认证守卫修改。无新增数据库迁移、依赖或环境变量。Dockerfile、流水线、生产配置不变。

支付服务中读取收据方法之前的代码，以及原有收据呈现和后续代码，均已与 main 作字符串逐段比对，完全一致。不能据此宣称零风险，但避免把其他资金逻辑带入本候选。

## 验证与边界

最终结果：后端 95 个测试集、994 项通过；main 基线 Node 回归 235 项通过；后端构建、入库敏感信息扫描及 diff 检查通过。

复核记录：首轮全量出现原上传 HTTP 用例的 `No mapping` 非 JSON 响应，单独复测通过；第二轮出现新增 HTTP 用例非预期 400。新增测试调整为整个测试集复用一个回环监听端口，不再逐请求启停临时端口；随后全量通过。未为通过测试修改生产业务逻辑，也未豁免失败用例。这些前序不稳定结果保留在此，不将一次最终通过解释为已完成云端验收。

- 后端全量单测、HTTP 路由测试、构建；小程序/仓库 main 基线 Node 回归。
- 新 HTTP 用例经过真实 Nest 路由及现有 AdminGuard/RolesGuard：未登录拒绝、业主令牌拒绝、员工不能用请求头伪造租户、手机号和页码保留、超长关键词拒绝。
- 服务层覆盖租户查询条件、同订单业主/管理收据一致、退款作废、未支付无凭证、搜索与计数条件一致。
- 使用模拟数据库和认证依赖，测试命令显式指定虚拟 DATABASE_URL。未连接生产数据库，未调用微信支付、退款或发消息。
- 尚未完成真实数据库集成、云托管镜像构建、生产只读验收和真机验收。测试通过不是已上线或资金全链路验收通过。

## 等用户授权后的步骤

1. 重新核对 main 未前进及候选差异；若基线变化，重新合并检查与回归，不强推。
2. 确认云托管当前可回滚镜像、备份状态、网络及环境变量保持原值；不新增环境变量，不改分支为整个管理端开发分支。
3. 用户此前将多项生产秘密贴入聊天，应另行安排凭据轮换。不能把秘密抄入文档/仓库，不能在本候选里擅自更换以免中断登录或支付。
4. 用户明确授权后，才将此独立候选合入 main 并触发云托管构建。确认实际构建提交与候选一致。
5. 用既有微信成功订单做只读验收：查列表、手机号/房号搜索、读收据，核对订单号/金额/收据号/快照。不要新增真实收款或退款来测试。
6. 确认业主原收据路径不回归；手机预览验证新管理收据及保存相册。异常先保留证据，按已确认旧镜像回滚，不修改或删除财务数据。

此候选仅为收据功能准备。管理端开发分支里其他新功能所需 API 不随本候选上线，不能据此发布整个管理端改造为“全部可用”。
